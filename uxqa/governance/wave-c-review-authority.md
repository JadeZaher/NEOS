# Wave C review: authority and data integrity

## Verdict

REQUEST_CHANGES. The platform-admin rule itself holds: it is computed once per request from an ACTIVE
co_creator/builder row in the home ecosystem, which is pinned by id. No `api/`, `agent/`, `mcp_server.py` or `views/`
code still reads `ctx.member.profile` as a global gate, and the four migrations upgrade a pre-wave PostgreSQL
database with data cleanly. Three HIGH defects still make the wave's "ironclad onboarding" and "platform admin only
by rule" claims false, and each was confirmed by a probe through `create_app`:

1. A member who left comes back with their old role and admin profile. A home owner who exits and rejoins is a
   platform admin and owner again, and no steward is involved.
2. The steward-only rule for onboarding content is enforced on one route but not on its siblings. Any signed-in
   member can rewrite, re-flag, delete or read the results of any ecosystem's quizzes.
3. The legacy DID login `/auth/verify` is a second placement path that skips `place_member`. It creates an ACTIVE
   row with no consent, in whatever ecosystem `select(Ecosystem).limit(1)` returns, including a private one.

Four MEDIUM findings follow:

- The agreement review can end twice: the agreement row is not locked.
- An ecosystem's founder is recorded as an independent auditor.
- Signed-out visitors can read posts on public profiles.
- Self-chosen admin profiles from before 2026-10-31 were never audited (PLAUSIBLE: production data not checked).

## What I checked and found sound

- Platform-admin predicate: `policy.is_platform_admin` (`api/policy.py:353-355`) requires an active row in the home with an admin profile. A NULL home fails closed.
- Home resolution: `helpers.home_ecosystem_id` (`api/helpers.py:52-65`) reads env then the pin, uses ids only, and returns None for a non-UUID or a missing ecosystem. An explicit env id that names nothing does not fall back to the pin.
- Middleware (`main.py:303-309, 336-338, 349-354, 400-404`): the flag is reset on every request (OPTIONS and anonymous included), set on both public and protected paths, and False when a lookup fails.
- `require_admin` (`api/helpers.py:29-36`) reads only `ctx.platform_admin`. Its only remaining call sites are platform-wide resources: settings, global badges and CTC hand-off (`api/settings.py:68`, `api/badges.py:70`, `api/ctc_handoff.py:56,75`). No `ctx.member.profile` or `is_profile_admin(request.ctx.member)` gate remains in `api/`, `agent/`, `mcp_server.py` or `views/`. The unused `is_profile_admin` import is still at `api/domains.py:45`.
- `PUT /settings` refuses the pin key (`api/settings.py:77-78`). No other `AppSetting` writer exists.
- Teams (`api/teams.py:66-77`): `get_scoped_or_404`, then `caller_in` and `can_administer_ecosystem`. `TeamUpdateRequest` has no `ecosystem_id`, and a team member must be in the team's ecosystem.
- Badges (`api/badges.py:67-85`): an ecosystem badge goes through `caller_in` and `can_administer_ecosystem`, a global one through `require_admin`, and a badge outside the caller's ecosystems reads 404. The update schema has no `ecosystem_id`.
- Profile grant (`api/members.py:612-640`): `can_grant_profile` on the target's ecosystem row: owner, or founder bootstrap. Self-choice of an admin profile is refused (`policy.py:334-337`, `members.py:490, 550`).
- Assistant and MCP: no tool touches settings, teams, badges, CTC, ethos access or quiz assignments. MCP acts as the token owner (`mcp_server.py:123-164`) and has no platform-admin path. `_exchange_tool` scopes to the owner's active ecosystems and relies on `confirm` as the MCP confirmation (`mcp_server.py:866-884`).
- Ethos access (`api/ethos_access.py:40-45, 151-155`) checks a steward there, the target in that ethos, and `granted_by` is the steward's row. Consent refuses exited and paused rows.
- Quiz assignments (`api/quiz_assignments.py:68-73, 123-158, 168-176`) check a steward of the member's or assignment's ecosystem. The list fails closed on an empty selection (`restrict_to_ecosystems`).
- Journey maps (`api/orientation.py:44-53, 251, 292, 330, 350`) require a steward of the map's ecosystem; a global map is 403; deleting a walked map is 409.
- Progress (`api/orientation.py:57-83`) takes only an active journey of that ecosystem and refuses exited and paused rows.
- Ecosystem quiz assign, unassign and results (`api/ecosystems.py:383-388, 436, 485, 507`) require a steward there, and another ecosystem's quiz is 403.
- `GET /ecosystems/:id/shares-needs` requires an active row (`api/ecosystems.py:570-572`).
- Placement (`services/member_lifecycle.py:111-157`): private ecosystems are 404 for new rows. The existing row is FOR UPDATE, a concurrent insert loses inside a savepoint (unique `uq_member_ecosystem_user`) and answers 409, and every move writes one transition.
- `POST /members` cannot create a row: scope requires an active row there, so it is 403 or 409.
- Steward moves (`api/policy.py:400-418`; `api/members.py:658-668`): a closed table, outranking required, never yourself, the target row locked, the refusal re-checked after the lock. The chat `move_member` re-checks after locking (`agent/governance_tools.py:4056-4078`).
- Newcomers list (`api/onboarding.py:154-196`) is limited to stewards of the selection, and is 403 otherwise.
- Exchange visibility: `can_see_publication` (`api/policy.py:455-472`) matches `visible_clause` (`services/exchange.py:165-183`) term for term. Stewards and domains come only from ACTIVE rows, and a hidden post is visible only to its author and the stewards. Every list (Discover, admin, domain, ecosystem, profile own, chat find) uses `visible_clause`, and detail uses `load_visible` with a 404 that has the same body as a missing post.
- Exchange IDOR: `domain_id` must belong to the ecosystem (`services/exchange.py:427-429`). `fulfilled_by` must be a responder (`:519-527`). `linked_share_need_id` must be visible, open, and in one of the two domains (`:801-806`). A private target domain without a row is 404 (`:786-789`). A post never moves ecosystem or domain (`:491-494`). Responders' names go only to the author (`:302`).
- Exchange races: write routes lock the post (`api/discover.py:343-352, 389-415`). Duplicate posts are serialised on the author row (`services/exchange.py:450`). Approve and end lock the collaboration (`api/discover.py:519-526, 545-553`, chat `_find_collaboration` `for_update=True`), and `uq_collaboration_approval_ecosystem` backs it.
- Collaboration approval (`api/policy.py:475-484`): same-ecosystem needs a steward who did not propose. Cross-ecosystem auto-approves the proposer's source side only, and the proposer never approves the target side, even with a steward row there.
- Exit withdraws open posts with "author left" (`api/exit.py:227-228`, `services/exchange.py:650-657`).
- Maintenance: ending a review needs findings of 8+ characters and a later next review date (`api/agreements.py` `review_outcome_refusal`), and writes a `ReviewRecord`. Rollback is limited to draft and advice, restores terms only, and is 409 `ROLLBACK_LOCKED` otherwise.
- Compliance scopes to one ecosystem through an active `caller_in` (404 otherwise), and `/latest` and `/history` use `restrict_to_ecosystems`.
- The health snapshot is for active members there only (`api/safeguards.py` `/snapshot`, 404). A domain steward or status change needs a steward who is not the domain's own steward, plus a reason (`api/domains.py:349-383`).
- Migrations:
  - `py -m alembic heads` gives `v1b4e7c9d2f5 (head)`, one head.
  - On a disposable PG16 DB built at `r6c1e8a4f2d7` with data, `alembic upgrade head` ran all four revisions. Results: the pin landed on the oldest "OmniOne" (not the later "omnione"); `private` became `domain`; " Skill " became `skills`; the exited author's post became withdrawn "author left"; the authorless post became withdrawn "No author on record"; `self_assessment` defaults false; five named FKs were created with SET NULL.
  - `downgrade r6c1e8a4f2d7` followed by `upgrade head` ran cleanly, and the pin was re-created once.
  - Every new column is nullable or has a server default; there are no NOT-NULL-without-default additions and no FKs over existing bad data (the new columns start NULL).
  - The models match the migrated schema.
  - The repo's PG migration and race tests: `18 passed`.
- UTC pin (`db/session.py:26-31`): added only for `+asyncpg` URLs, after `_ensure_async_url`. SQLite is untouched. It changes only what `now()` stores in `timestamp without time zone` defaults, so it changes nothing in production if the server zone is already UTC (Railway's default). That could not be checked here: the local PG runs in America/Denver, and I did not contact `*.rlwy.net`. The MCP engine (`mcp_server.py:107`) applies it to the raw URL, which matters only when that URL already names `+asyncpg`.
- Baseline: the wave's own backend tests (`test_platform_admin`, `test_onboarding_*`, `test_exchange_*`, `test_g_health`) on SQLite gave `378 passed, 1 skipped`.
