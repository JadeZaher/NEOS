# Decision routing and operator quality

The member's prompt should select a useful governance skill or receive a direct platform/framework explanation. Loading a formal process for a simple definition adds friction, while using stale skill prose can contradict the current lifecycle engine.

Use OpenRouter's typed Decisions API for bounded routing judgments. Keep Gemini 3.1 Flash-Lite for answers and operator tool use. Both model paths stay low cost and non-Anthropic. The decision model receives only the prompt, bounded relevant conversation/page context and public skill metadata; it never grants authority, supplies tool arguments or overrides confirmation rules.

## Acceptance

- An independent skill-usefulness probability gates the skill choice. Direct platform, framework and general outcomes explicitly clear old skills.
- Explicit manual skill selection is validated; automatic selection is reconsidered on each prompt and after topic changes.
- A pinned model is chosen through representative positive, negative, ambiguous and adversarial probes. Record raw probabilities, actual model, latency and cost. Malformed, unavailable or disabled decisions use a direct fallback.
- Current lifecycle rules and actual tool outcomes take precedence over static skill text. Advice never advances automatically.
- Close prior operator gaps: unsupported historical explanations, repeated unresolved searches, reading level, incomplete exit guidance, ecosystem clarification, and invented drafting details.
- Preserve conversation/session/draft across close, tabs and record navigation. Keep the operator available on Messaging. Show understandable routing labels, safe refusal reasons, accurate confirmation copy, limit recovery and accessible announcements.
- Revisit all seven gold journeys, including orientation and repeat response delivery, plus constrained keyboard/mobile journeys.
- Source review is independent. Apply fixes before one integrated unit/typecheck/build sweep. Each QA finding and any unresolved coverage has reproducible evidence.

## Node support administration

The node can assign multiple global NodeAdmins. Their public badge identifies technical support operators who assist all organizations and users, including organizations in which they hold no membership. Authority comes from an explicit User assignment, never a self-selected ecosystem profile. Initial assignments require a vetted bootstrap User allowlist; historical builder/co-creator profiles are not promoted automatically.

The administration page supports unilateral application-state management through declared capabilities, including reversible correction of governance evidence and proposals on behalf of an organization. Record the actual operator and organization; do not fabricate a member identity, consent or historical authorship. Preserve original evidence privately when archiving or restoring it.

Every administrative intervention has an immutable public receipt showing the actor, target, reason and outcome with safe change metadata. Public history and the active operator roster are accessible without membership. Private inspected content, credentials and original archived evidence remain protected. Failed and denied attempts are durable; new commands and their successful audit entry commit atomically. Concurrent revocation or disabling cannot remove the final usable NodeAdmin.

The personal assistant offers an explicit organization-bound support mode to assigned NodeAdmins, including Users with no membership. It uses the same audited command service and private owner-only support conversations. Confirmation executes the exact reviewed arguments under fresh authorization, including after role revocation or target changes.
